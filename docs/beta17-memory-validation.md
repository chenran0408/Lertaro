# Beta17：搜索的临时分配

本项减少同一次搜索中的中间数据：匹配阶段每处理一块名称便消费、清空工作缓冲，名称搜索不再积攒全量命中列表；路径阶段沿用原有父目录查找和重命名处理，记录目录行号，直接将 UTF-8 名称写入最终路径。取消每层目录的临时名称字符串和中间 StringBuilder；不增加常驻缓存，不改变索引格式。

## 验证环境与方法

- 同机 Windows x64、.NET 10、Release 构建。
- 只读冻结索引：2,561,447 条记录，962,086 个唯一名称；没有修改用户索引或设置。
- 独立进程运行，先按相同查询预热，再记录分配、耗时、CPU、私有内存、工作集、IO 和结果摘要；没有强制 GC 或清空工作集。
- 累计分配用 `GC.GetTotalAllocatedBytes` 统计，不能当作同时驻留的内存。
- IO 计数来自进程读写计数；内存映射缺页另计，读写计数为零不代表完全没有磁盘访问。

## 路径生成定向实验

对同一索引的 100,000 条记录逐条生成路径，前后摘要一致。

| 指标 | 修改前 | 直接生成最终路径 |
| --- | ---: | ---: |
| 累计分配 | 132,443,592 B | 22,347,952 B |
| 每条路径平均分配 | 1,324.4 B | 223.5 B |
| 单次实验耗时 | 131.6 ms | 124.2 ms |

路径生成部分少分配 110,095,640 B（约 105 MiB，83.1%）。此数字仅对应上述路径实验，不能代表整个 App 的内存降幅。

## 正确性

148 项相关 Delta/Search 测试通过，包含跨多个块的完整匹配、命中不重复、缓冲大小上限、中文、四字节 UTF-8 名称、UNC 根目录、重命名祖先、未解析父目录及深目录边界。索引和返回结果没有被截断。

另外，按行号遍历冻结索引全部 2,561,447 条记录，旧版与最终候选的路径累计摘要均为 `99FA284028443B92`。`pcl` 两档查询的数量和有序摘要均一致。

早期实验未记录处理器环境，出现过宽泛查询摘要差异，未采用其性能结论。最终查询实验明确将两组均设为 20 个逻辑处理器，每个子进程独立记录运行时处理器数量，三组查询的数量和有序摘要均三轮一致。

## 最终搜索实验

旧版为当前已安装的 Beta16 Core，候选包含直接路径生成和分块消费。每组运行三个独立进程，表中为中位数；只统计一份冻结索引的查询，不代表完整 App 启动或全盘汇总。

| 查询／结果上限 | 累计分配：旧版 → 候选 | 耗时：旧版 → 候选 | CPU 时间：旧版 → 候选 |
| --- | ---: | ---: | ---: |
| `pcl`／51 | 11.98 → 1.19 MiB | 22.87 → 20.58 ms | 0.1094 → 0.0781 s |
| `pcl`／全部（161,554 条） | 425.41 → 225.70 MiB | 770.65 → 804.60 ms | 0.8750 → 0.8906 s |
| `a`／100,000 | 1,058.54 → 612.46 MiB | 1,455.27 → 1,427.04 ms | 1.9844 → 2.0625 s |

上述三组查询结束时的私有内存分别为 27.25→14.13、48.76→44.14、336.17→227.12 MiB；私有内存峰值为 27.26→14.13、51.78→49.77、336.18→299.89 MiB。工作集为 106.11→95.03、180.84→177.13、486.86→352.78 MiB。18 个进程的读写传输计数均为零，映射缺页另有记录。

限制：完整 `pcl` 查询的中位耗时增加约 34 ms（4.4%），宽泛查询 CPU 时间增加约 3.9%；本版以减少大块临时分配和搜索期间内存为收益，不能宣称所有查询都更快。常用快速搜索在本组数据中约快 10%。

## 范围限制

App 的原生渲染资源、输入法和其他功能仍有占用。本项不承诺 50 MB 常驻内存，也不把工作集自动下降当作优化成果。软件渲染和延迟创建窗口的实验未采用；前者涉及现有硬件加速设置及性能取舍，后者使首次唤起明显变慢。排序缓冲重构的实际搜索收益不足，也未纳入本版。
