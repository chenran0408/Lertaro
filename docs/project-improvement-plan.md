# 项目改进安排（2026-10-30）

## 先说 Rust 为什么没有显示

这不是 Rust 没有进入仓库。当前 `main` 已包含 `Core/NativeIndexStore`，GitHub Languages API 返回 Rust 53,882 bytes，约占 0.50%。截图对应的是 GitHub 语言统计尚未刷新时的结果；刷新仓库页面或稍后重新打开即可看到 Rust。Rust 占比小也正常：Lertaro 是以 C# 为主的 Windows WPF 应用，Rust 目前集中在索引存储和快照/压缩构建。

截图中的 “No contributors” 也是 GitHub 贡献者统计缓存/归因状态，不代表没有提交。当前提交已经能归因到 `chenran0408`。

## 三个最大的短板

### 1. 对外仓库身份曾经不一致（已修复）

多语言 README 的下载和安全链接仍指向旧的 `Lertaro/Lertaro`，会造成下载失败和安全判断混乱。已统一改为 `chenran0408/Lertaro`，并在 Beta CI 中加入旧链接检查，防止再次回归。

### 2. 性能优化缺少持续的回归基线（下一步）

当前已经有快照/压缩基准，但性能数据还没有进入 CI 门禁；Rust 只占约 0.5%，继续把代码搬到 Rust 并不会自动带来收益。下一轮先固定搜索延迟、压缩耗时、分配量和工作集四项指标，按真实索引分布比较，只有稳定获益才继续扩大 Rust 范围。

### 3. 核心功能集中在大型 C# 调用链，长期维护成本高（持续治理）

代码库当前约 2,311 个 C# 文件、约 6 个 Rust 文件，搜索、插件、更新、WPF 交互之间耦合面较大。下一阶段不做大范围重写，按高频路径拆分边界：先处理搜索/别名和索引发布的可测热点，每项改动配套定向回归、x64/ARM64 验证和一次完整发布验证。

## 后续十轮安排

1. **第 1–3 轮：** 建立可重复的搜索与压缩性能基线，确认别名生成、路径匹配、快照写入的真实热点。
2. **第 4–6 轮：** 只实施基线证明有效的优化；同时补齐大索引、中文别名、硬链接、异常更新和普通用户更新回归。
3. **第 7–8 轮：** 清理高耦合边界，减少重复的 C# 中间对象；Rust 仅承担已经测出收益的纯数据处理部分。
4. **第 9 轮：** 完成 x64/ARM64 安装、升级、静默更新、签名和真实索引压力验证。
5. **第 10 轮：** 冻结功能，执行完整测试和发布门禁；全部通过后再发布正式版。

每一轮保持“一个问题、一个可测改动、一次完整验证”，不为了让 GitHub 显示更多 Rust 而重写没有收益的代码。
